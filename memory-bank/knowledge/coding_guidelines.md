# 编码规范

## Python 风格
- **遵循 PEP 8**: 使用 black (line-length=120)
- **类型提示**: 使用 Python 3.10+ type hints
- **文档字符串**: 关键函数需要 docstring

## 错误处理原则
遵循全局 CLAUDE.md 中的 Python 异常处理指南:

### 1. 默认不使用 try/except
- 假设代码在正常情况下运行正确
- 信任输入参数有效、文件系统可用、内存充足

### 2. 快速失败原则
- 如果操作失败 (文件写入、绘图、网络请求等),立即抛出异常
- 不在模块内静默处理或记录错误后继续执行
- 让异常带着完整错误信息和堆栈传播给调用者

### 3. 委托错误处理给调用者
- 只有调用者知道如何恰当处理特定错误
- 调用者可选择重试、回滚、显示用户消息或终止程序
- 底层模块不应假设错误应如何处理

### 4. 优先代码简洁性
- 移除防御性 try/except 块
- 减少样板错误处理代码
- 保持函数逻辑清晰专注

### 何时使用 try/except
仅在以下情况使用:
- 提供额外错误上下文
- 在有限情况下优雅降级
- 在适当抽象层级捕获并重新抛出

## 模块组织
- **单一职责**: 每个模块/类专注一个功能
- **依赖注入**: 避免全局单例,通过参数传递依赖
- **显式优于隐式**: 明确数据流和依赖关系

## 配置管理
- **YAML 优先**: 训练配置使用 YAML 文件
- **Dataclass/Pydantic**: 使用类型化配置类
- **argbind**: CLI 参数绑定

## 测试策略
- **测试行为**: 测试接口行为而非实现细节
- **确定性**: 测试应可重复、无随机性
- **单一断言**: 尽可能每个测试一个断言

## 提交规范
- **小步提交**: 增量式可编译可测试的提交
- **清晰消息**: 说明"为什么"而非"做什么"
- **格式化**: 提交前运行 black
- **测试通过**: 确保所有测试通过

## 代码审查重点
- 是否引入不必要的复杂度?
- 是否遵循项目现有模式?
- 错误处理是否合理? (快速失败 vs 静默吞异常)
- 是否有足够的类型提示?
